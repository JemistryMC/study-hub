# Exo Academic Platform

منصة Exo لإدارة المحاضرات وملفات الدراسة والتخطيط الأكاديمي. هذا المستودع هو المصدر المرجعي الوحيد للكود والتقارير.

## ابدأ من هنا

1. اقرأ [تعليمات Gemini](GEMINI.md).
2. راجع [الحالة الحالية للمشروع](reports/CURRENT.md).
3. افتح [المرحلة الأمنية النشطة](reports/phases/phase-4.2.4.4.1/README.md).
4. راجع [طريقة العمل والتقارير](reports/README.md).

## خريطة المشروع

| المسار | وظيفته |

| `index.html` | التطبيق الحالي ومنطقه وواجهة المستخدم |
| `server.js` | خادم التطوير وتقديم الملفات |

| `reports/` | تقارير المراحل والمراجعات وسجل التسليم |

## الفروع: أين يعمل Gemini؟

نعتمد الآن سير العمل التالي:

| الفرع | الاستخدام |
| --- | --- |
| `main` | **فرع العمل النشط لـ Google AI Studio / Gemini**. كل التعديلات الجديدة تُحضّر هنا وتظل غير معتمدة حتى المراجعة. |
| `Deploying` | نسخة مرجعية محفوظة من خط الأساس السابق. لا يعمل Gemini عليها في هذه الدورة. |
| `backup/pre-gemini-security-2026-11-04` | نقطة استرجاع من حالة `main` قبل بدء العمل الأمني الجديد. لا تحذفها. |

وجود التعديلات على `main` لا يعني أنها معتمدة أو جاهزة للنشر. نتعامل معها كتغييرات مرشحة للمراجعة.

## دورة العمل — تحكم المالك

1. Gemini يقرأ `GEMINI.md` و`reports/CURRENT.md` وملف المرحلة النشطة.
2. Gemini يفحص النسخة المتصلة، ويعدّل نطاق المرحلة فقط.
3. قبل أي مزامنة يعرض Gemini قائمة الملفات المتغيرة والـ Diff والاختبارات والـ Base SHA.
4. المالك يراجع التغييرات داخل Google AI Studio ويتأكد أن المستودع هو `JemistryMC/study-hub` والفرع هو `main`.
5. المالك وحده يقرر تنفيذ GitHub Sync. إذا كانت الواجهة لا تقدم إلا `Force push to main`، لا يتم الضغط إلا بعد مراجعة الـ Diff والتأكد من وجود نسخة الاسترجاع المذكورة أعلاه؛ فالـ Force Push قد يعيد كتابة تاريخ الفرع.
6. بعد المزامنة نتحقق من Commit SHA والملفات الفعلية وGitHub Actions على نفس SHA.
7. المراجعة المستقلة والموافقة الصريحة مطلوبة قبل اعتبار المرحلة معتمدة أو السماح بالنشر.

## قواعد غير قابلة للتجاوز

- لا أسرار أو مفاتيح أو كلمات مرور أو ملفات `.env` أو JWTs في Git.
- لا اتصال بـ Supabase Production ولا تطبيق migrations على قواعد بيانات حقيقية.
- لا حذف للاختبارات أو تخفيف Assertions لإظهار نجاح زائف.
- لا اعتبار للـ mock أو PGlite كدليل على PostgreSQL 16 الحقيقي.
- لا تعديل للواجهة أو إضافة مميزات أثناء إغلاق المرحلة الأمنية.
- لا تغييرات في `Deploying` أو فرع الاسترجاع دون طلب صريح.
- كل نتيجة اختبار يجب أن ترتبط بـ SHA محدد؛ افصل الاختبار المحلي عن GitHub Actions.
