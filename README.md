# Exo Academic Platform

منصة Exo لإدارة المحاضرات وملفات الدراسة والتخطيط الأكاديمي. هذا المستودع هو **المصدر الوحيد المعتمد للكود**.

## ابدأ من هنا

1. اقرأ [تعليمات Gemini](GEMINI.md) قبل أي تعديل.
2. راجع [الحالة الحالية](reports/CURRENT.md).
3. راجع [دليل التقارير والمراحل](reports/README.md).
4. المهمة النشطة: [Phase 4.2.4.4.1](reports/phases/phase-4.2.4.4.1/README.md).

## خريطة المشروع

| المسار | وظيفته |
| --- | --- |
| `index.html` | التطبيق الحالي وواجهة المستخدم والمنطق الأمامي |
| `server.js` | خادم التطوير وتقديم الملفات |
| `build.js` | تجهيز نسخة التوزيع الثابتة |
| `sw.js` و`manifest.json` | PWA وملفات التشغيل |
| `supabase/migrations/` | تغييرات قاعدة البيانات المتسلسلة |
| `supabase/schema.sql` | مرجع مخطط قاعدة البيانات |
| `supabase/rollbacks/` | خطط التراجع الموثقة |
| `test_*.js` و`run_*.js` | اختبارات الأمان والتكامل والمتصفح |

## الفروع وقواعد العمل

| الفرع | الاستخدام |
| --- | --- |
| `main` | النسخة المرجعية المعتمدة والتقارير |
| `Deploying` | فرع التطوير النشط: الكود والاختبارات والـ migrations قيد المراجعة |

**Gemini يعمل على `Deploying` فقط.** لا تعدّل `main` ولا تدفع إليه.

قبل استيراد المستودع في Google AI Studio، تأكد أن الفرع المرتبط هو `Deploying`. إذا كان AI Studio يستخدم الفرع الافتراضي فقط، غيّر الفرع الافتراضي للمستودع إلى `Deploying` من GitHub Settings → General → Default branch، ثم أعد الاستيراد وتأكد من اسم الفرع في واجهة GitHub داخل AI Studio.

إذا لم تستطع التأكد أن المزامنة ستصل إلى `Deploying`، **توقف ولا تعمل Sync**. لا تستخدم Force Push إلى `main` مطلقًا.

## دورة العمل

1. Gemini يقرأ `GEMINI.md` و`reports/CURRENT.md` وملف المرحلة النشطة.
2. Gemini يفحص الكود الحالي ثم ينفذ نطاق المرحلة فقط.
3. يشغّل الاختبارات ويعرض Diff ونتائج خامًا مرتبطة بالنسخة التي اختبرها.
4. صاحب المشروع يراجع قائمة الملفات والفرع وملخص التغييرات قبل الضغط على Sync.
5. تتم مراجعة GitHub Actions والـ Diff على Commit SHA الفعلي.
6. لا ينتقل أي تغيير إلى `main` قبل مراجعة مستقلة وموافقة صريحة.

## قواعد غير قابلة للتجاوز

- لا أسرار أو مفاتيح أو كلمات مرور أو ملفات `.env` في Git.
- لا تغييرات إنتاجية أو migrations على Supabase الفعلية.
- لا حذف لاختبارات أو تخفيف Assertions لإظهار نجاح زائف.
- لا اعتبار للـ mock أو PGlite كدليل على PostgreSQL 16 أو Supabase الحقيقي.
- لا إضافة مميزات UI أو إعادة تصميم أثناء إغلاق مرحلة الأمان.
- كل نتيجة اختبار يجب أن ترتبط بـ SHA محدد؛ لا تخلط الاختبار المحلي مع GitHub Actions.
